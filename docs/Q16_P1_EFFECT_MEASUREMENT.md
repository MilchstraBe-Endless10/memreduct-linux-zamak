## 三问分开答

### ① 写对目标了吗 —— 是
target 精确指向该 scope 的 `memory.reclaim`，带 `swappiness=0`（不换出匿名页），
两次写入 `errno=0 class=accepted`。

### ② 目标计数怎么变 —— 先降 26.5 MB，60 秒内完全反弹并超过基线
- `file` 124.6 → 98.1（−26.5 MB，−21%）→ 158.8（**比清理前多 34.2 MB**）
- `inactive_file` 105.4 → 75.8 → 128.6
- `anon` 几乎不动（48.7 → 48.2），符合 `swappiness=0` 的承诺
- **`workingset_refault_file` 只涨 0.03 MB**（12.29 → 12.32）

关键判据：**反弹不是"快速重读"，不是刚才清掉的页被立刻读回来。**
refault 几乎零增长，说明降下去的那些文件页大部分没有被重新读取；
上来的 34 MB 是 Chrome 在这 60 秒里**新写的**页缓存。

### ③ 日常收益 —— 未证实，且这次拿到了反证
60 秒后文件页比清理前还多。对活跃应用做一次性文件页回收，
在被同一工作负载继续使用的情况下，一分钟内就失效了。

## 这组数据的意义

它回答了一个此前只能推测的问题：**Balanced clean 对正在使用的应用有没有持续作用。**
答案在这一次测量里是「没有」。这不是缺陷，是"清理缓存"这个动作本身的性质——
但产品文案和预期必须与之一致，不能暗示清理后内存会持续更低。

## 不能从这组数据推出的结论
- 不能推出"所有应用都没用"：Chrome 是活跃负载，后台挂起的应用行为可能不同
- 不能推出"应该加大请求量"：33.5 MB 已经回收了 26.5 MB，内核给得够
- 不能推出"应该调阈值"：refault 没涨，说明现有 `swappiness=0` + 文件页优先的选择是对的
