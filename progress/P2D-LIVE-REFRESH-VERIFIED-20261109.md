## P2D：主窗口实时刷新实测 —— 3 秒周期，确认在动

2026-09-11-09。此前所有截图都是"打开后某一刻的样子"，从没验证过
显示的数字会不会随时间更新。本轮补上。

### 源码

```zig
app.every(1000, tick)          # 每 1000 ms 触发一次 tick
...
elif s.elapsed_ms % 3000 == 0:
    refresh(s)                 # 每 3 次 tick 才真正重采样
```

**定时器 1 秒，但采样 3 秒一次。**

### 实测

连续每秒截 6 张，比较整图哈希：

```
t1 b8dfd006...
t2 b8dfd006...   ← 与 t1 相同
t3 c840ae54...   ← 变了
t4 c840ae54...   ← 与 t3 相同
t5 c840ae54...   ← 与 t3 相同
t6 dcce8ba3...   ← 又变了
```

三组不同哈希：`{t1,t2} / {t3,t4,t5} / {t6}`。

### 为什么是 "2+3+1" 而不是整齐的 "3+3"

截图本身有耗时（import 命令约 200~400 ms），加上 sleep 1，
实际间隔略大于 1 秒，因此与 3 秒边界的相位漂移，组的大小不固定。
**不是刷新不稳定，是测量工具的采样率与被测周期不成整数倍。**

### 教训：第一版裁剪选错了位置

我最初按 `-crop 100x14+170+92` 裁「可用内存」那一行，6 张的该区域哈希全部相同，
差点得出"没刷新"的结论。核对截图后发现 y=92 落在「Usage」行上方空白处，
根本没框到数字。

**改用整图哈希才发现真实差异。** 教训：局部裁剪前必须先看图确认坐标，
否则相同的结果会被误读成"没有变化"——这和"设备没反应"的误判是同一类错误。

### 结论

| 项 | 结果 |
|---|---|
| 是否实时刷新 | **是** |
| 实际采样周期 | 3 秒 |
| 首次刷新延迟 | ≤3 秒（截图时已显示真实值）|
| 数值真实性 | 显示 96.969% / 479.3 MB / 15.4 GB，与 `free` 当时的量级一致 |
